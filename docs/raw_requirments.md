# 简易审批流系统 — 实习生开发任务书

> **项目周期：5 个工作日（1 周）**  
> **项目类型：前后端全栈开发实战**  
> **开发方式：独立开发，每人提交一套完整项目**  
> **目标：通过一个小型审批业务项目，练习需求分析、数据库设计、前端页面、API 开发、权限校验、状态流转、事务一致性、测试及 Git 交付。**

## 一、项目背景

公司希望开发一个简易审批流系统，支持员工提交申请、审批人处理申请、申请人查看进度和审批历史。

本期仅实现**固定两级串行审批**，不要求接入 Flowable、Power Automate 等工作流引擎，也不要求设计通用流程设计器。要求完成**前端页面 + 后端 API + 关系型数据库**，所有核心业务必须能通过浏览器操作；Swagger / Postman 仅用于辅助调试。

请根据业务需求自行设计数据库、接口和代码结构。未明确规定的实现细节可合理决定，但须在 README 或 Spec 中说明。

## 二、技术要求

可根据个人熟悉程度选择技术栈，**不要求所有技术都使用**。

| 模块 | 可选技术 | 要求 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite / React + Vite | 二选一，推荐 TypeScript；允许 JavaScript |
| UI 组件 | Element Plus / Ant Design / Ant Design Vue / 原生 CSS | 自由选择，页面可用即可 |
| 后端 | ASP.NET Core Web API（.NET 8+）/ Python FastAPI / Django REST Framework | 任选一种 |
| 数据库 | PostgreSQL（PgSQL）/ SQL Server / MySQL | 任选一种，必须使用关系型数据库 |
| 数据访问 | EF Core / Dapper / SQLAlchemy / Django ORM | 与后端技术栈匹配 |
| 身份认证 | JWT Bearer | 必做，后端必须验证 Token |
| API 文档 | Swagger / OpenAPI | 必做 |
| 测试 | xUnit / pytest / 对应框架测试工具 | 至少覆盖关键业务规则 |
| 版本管理 | Git | 必做 |
| 日志 | .NET Logging / Serilog / Python logging | 后端记录异常 |
| 部署 | 本地启动；Docker Compose 可选 | 必须提供可复现启动步骤 |

**建议组合（仅供参考）：**

- 组合 A：Vue 3 + ASP.NET Core Web API + PostgreSQL + EF Core。
- 组合 B：React + FastAPI + PostgreSQL + SQLAlchemy。
- 组合 C：Vue 3 + Django REST Framework + PostgreSQL。
- 组合 D：React + ASP.NET Core Web API + SQL Server + Dapper。

**工程要求：**

- 前后端分离，前端通过 HTTP API 调用后端，不得直接连接数据库。
- 后端有清晰的职责划分，避免将所有业务逻辑放在 Controller / Router 中。
- 前端按页面、API 请求、公共组件等职责组织代码。
- 不提交真实密码、密钥或敏感配置；用户密码必须安全哈希存储。
- 核心审批规则必须由后端校验，不能只靠前端隐藏按钮。
- 能够解释和独立修改核心代码。

## 三、功能需求

### 3.1 用户注册与登录

系统需要支持：

1. 用户注册：用户名、密码、显示名称。
2. 用户登录：通过用户名和密码获取 JWT。
3. 获取当前登录用户信息。
4. 用户名不可重复；密码不得明文存储，使用安全哈希算法。
5. 除注册、登录外，所有业务接口必须登录。
6. 所有注册用户均可创建申请；是否能审批由其是否被指定为当前审批人决定，不需要额外实现管理员角色。

**验收场景：**

- 注册至少三名用户：申请人、一级审批人、二级审批人。
- 重复用户名注册失败，错误密码登录失败。
- 不携带 Token 访问申请接口返回 HTTP 401。

### 3.2 申请单管理

每张申请单至少包含以下信息：

| 字段 | 说明 |
| --- | --- |
| Id | 申请单唯一标识 |
| Title | 申请标题，必填，最长 100 字符 |
| Content | 申请内容，必填，最长 2000 字符 |
| Status | 草稿、审批中、已通过、已驳回 |
| ApplicantId | 申请人，由当前登录用户确定 |
| FirstApproverId | 一级审批人 |
| SecondApproverId | 二级审批人 |
| CurrentStep | 当前审批步骤；草稿或已结束时可为空 |
| CreatedAt | 创建时间 |
| UpdatedAt | 最近更新时间 |
| SubmittedAt | 最近一次提交时间，可为空 |

需要实现：

1. 创建申请单，初始状态为**草稿**。
2. 申请人编辑草稿的标题、内容及两级审批人。
3. 申请人提交草稿，进入一级审批。
4. 查看申请单详情，包括申请内容、当前状态、当前审批人和历史记录。
5. 查询申请列表，支持分页、状态筛选、标题关键词搜索；分页结果需返回总条数。
6. 提供“我发起的”和“待我审批”两个视图或筛选入口。
7. 申请人可删除自己的草稿；审批中或已结束的申请不可删除。

**权限规则：**

- 申请人可查看自己的申请；被指定的一级、二级审批人可查看自己参与的申请。其他用户不可查看申请详情或审批记录，返回 403。
- 只有申请人可以编辑、提交或删除草稿。
- 只有**当前审批步骤的指定审批人**可以审批；不能代替其他人审批，也不能提前审批下一节点。
- 申请人不得审批自己提交的申请：创建或修改草稿时，两级审批人都不得等于申请人。
- 两级审批人必须是已存在用户；本期允许一级与二级审批人为同一人，但该用户仍需分别完成两个步骤。
- 已通过的申请不可再次编辑、提交或审批。

### 3.3 固定两级审批流程

本期固定流程如下：

```text
创建申请
   ↓
  草稿 ── 提交 ──→ 一级审批中
                     ├── 通过 ──→ 二级审批中
                     │               ├── 通过 ──→ 已通过（结束）
                     │               └── 驳回 ──→ 已驳回（结束）
                     └── 驳回 ──→ 已驳回（结束）
```

**规则：**

1. 只有草稿可以提交；提交后状态为“审批中”，当前步骤为一级审批。
2. 一级审批人通过后，当前步骤变为二级审批，申请仍为“审批中”。
3. 二级审批人通过后，申请状态变为“已通过”，流程结束。
4. 任一审批人驳回后，申请状态变为“已驳回”，流程结束，不再继续后续审批。
5. 审批操作必须填写意见：通过时意见可为空，驳回时意见必填（最长 500 字符）。
6. 不允许跳过节点、重复审批、对已结束申请继续审批。
7. **本期不实现驳回后修改重提、撤回、会签、转交、加签、动态修改审批人、流程设计器。**这些可作为后续扩展讨论，不得影响本期核心交付。

### 3.4 审批记录与操作历史

每次**成功提交或审批**都必须保留记录，至少包含：

- 申请单 ID
- 操作类型（提交、一级通过、二级通过、一级驳回、二级驳回；也可使用步骤与动作分别记录）
- 操作人 ID
- 审批步骤（提交时可为空）
- 操作意见（可为空）
- 操作前状态 / 步骤、操作后状态 / 步骤
- 操作时间

需要提供按申请单 ID 查询历史记录的接口，按操作时间升序返回；同一时间的记录应有稳定的次级排序方式。

历史记录不可由普通用户修改或删除。删除草稿时不得产生误导性的审批记录。

**事务要求（必做）：**

> 提交申请或执行审批时，申请单状态 / 当前步骤更新与历史记录写入必须在同一个数据库事务中完成：两者要么同时成功，要么同时失败。

验收时需解释事务边界，并通过测试或演示证明历史记录写入失败时申请状态不会改变。

### 3.5 防止重复审批与并发覆盖

- 同一审批步骤成功处理后，旧请求再次提交必须被拒绝，不能新增重复历史记录。
- 后端应根据数据库中的**当前状态、当前步骤和当前审批人**判断操作是否有效，不得信任前端提交的当前步骤。
- 对两个请求同时审批同一节点的情况，必须保证最多只有一个请求成功推进流程。可采用乐观并发控制、条件更新、行锁或其他与数据库兼容的方案。
- 需要在技术设计中说明采用的防重复或并发处理策略，并提供验证步骤。

### 3.6 统一异常处理与参数校验

要求：

- 校验必填项、字符串长度、分页参数、审批人是否存在、审批意见等。
- 申请不存在返回 404；未登录返回 401；无权限返回 403；参数不合法返回 400；状态冲突或重复审批可返回 409（须统一）。
- 使用统一异常处理机制，避免每个 Controller / Router 重复捕获异常。
- 业务错误返回可读信息，内部异常不直接暴露堆栈或敏感数据。
- 服务器内部错误记录日志并返回 500。

可自行设计统一响应格式，但须在 README 中说明。

### 3.7 前端页面（必做）

必须提供浏览器可操作的前端界面，至少包含：

| 页面 / 功能 | 具体要求 |
| --- | --- |
| 注册页 | 输入用户名、密码、显示名称；展示校验结果 |
| 登录页 | 登录后进入业务页面；未登录限制访问 |
| 我发起的申请 | 展示标题、状态、当前步骤、创建时间；支持分页、状态筛选、关键词搜索 |
| 新建 / 编辑申请 | 编辑标题、内容、一级与二级审批人；草稿可保存和提交 |
| 申请详情 | 展示申请内容、申请人、审批人、当前步骤、状态 |
| 待我审批 | 展示当前需要本人处理的申请，支持进入详情 |
| 审批操作 | 当前审批人可通过或驳回；驳回意见必填；提交后刷新状态 |
| 审批历史 | 按顺序展示提交及审批操作、操作人、意见、时间 |
| 通用交互 | 加载状态、空数据提示、成功 / 失败反馈、表单校验、退出登录 |

**前端验收要求：**

1. 所有核心业务均可通过浏览器完成，不得只依赖 Swagger / Postman。
2. API 请求统一封装并携带 JWT；Token 失效时引导重新登录。
3. 根据当前用户和申请状态控制可见操作，但权限最终由后端验证。
4. 页面布局清晰，在桌面浏览器正常使用；不要求复杂动效和移动端适配。
5. 不强制使用特定状态管理库。

## 四、API 参考清单

以下规定接口能力，具体路由、DTO 和查询参数可合理调整，并在 Swagger 中体现。

| 方法 | 参考路由 | 功能 |
| --- | --- | --- |
| POST | `/api/auth/register` | 注册 |
| POST | `/api/auth/login` | 登录并获取 Token |
| GET | `/api/users/me` | 获取当前用户 |
| GET | `/api/users` | 获取用户简要列表（用于选择审批人） |
| POST | `/api/requests` | 创建草稿 |
| GET | `/api/requests/{id}` | 查看申请详情 |
| GET | `/api/requests?scope=mine&page=1&pageSize=10&status=...&keyword=...` | 分页查询我发起的申请 |
| GET | `/api/requests?scope=pending&page=1&pageSize=10` | 分页查询待我审批 |
| PUT | `/api/requests/{id}` | 修改草稿 |
| DELETE | `/api/requests/{id}` | 删除草稿 |
| POST | `/api/requests/{id}/submit` | 提交申请 |
| POST | `/api/requests/{id}/approve` | 当前节点审批通过 |
| POST | `/api/requests/{id}/reject` | 当前节点审批驳回 |
| GET | `/api/requests/{id}/history` | 查看审批历史 |

分页默认值建议为 `page=1`、`pageSize=10`，最大 `pageSize=100`。申请 ID 不存在返回 404；用户无权查看时返回 403（也可为避免资源枚举统一返回 404，但须说明并保持一致）。

## 五、数据库设计要求

请自行完成数据库设计，不提供现成建表脚本。至少覆盖**用户、申请单、审批历史**三类数据，可根据设计增加审批节点表或其他表，但不要求搭建通用流程引擎。

需提交：

1. ER 图（图片或 Markdown 内 Mermaid 均可）。
2. 数据库建表脚本或 ORM Migration。
3. 主键、外键、必要索引的设计说明。
4. 初始测试数据准备方式（脚本或自动生成均可）。
5. 申请状态、当前步骤与审批记录的关系说明；并发控制方案及相关数据库约束说明。

建议重点考虑：申请人和两级审批人的用户关联、申请单与历史的一对多关系、待审批列表的查询条件、历史排序及事务一致性。

## 七、测试与验收要求

至少完成以下场景的验证，其中**第 3、4、7、8 项必须提供自动化测试**（第 7 项建议使用集成测试），其余可通过测试代码或手动验收记录证明：

1. 创建申请单后状态为草稿，只有申请人能编辑和提交。
2. 提交后进入一级审批；未提交的草稿不出现在待审批列表。
3. 非当前审批人不能执行通过或驳回。
4. 一级审批通过后进入二级审批，不能直接结束为已通过。
5. 二级审批通过后状态变为已通过，后续审批被拒绝。
6. 一级或二级驳回后流程结束，驳回意见不能为空。
7. 审批历史写入失败时，申请状态和当前步骤更新回滚。
8. 对同一审批节点重复审批被拒绝，不产生重复记录；并发请求最多一个成功。
9. 申请人不能选择自己作为审批人。
10. 无关用户不能查看申请详情及历史；未登录访问接口被拒绝。
11. 分页查询返回正确总条数，待我审批列表仅包含当前需要本人处理的申请。
12. 浏览器可完整完成注册登录、创建草稿、提交、一级审批、二级审批、查看历史。
13. 前端正确显示错误、加载状态和空列表。

验收时除正常流程外，还会尝试越权、重复审批、非法状态变更，并随机提出一项小幅需求变更。需能解释实现方式和修改思路。

## 八、Git 与交付规范

每人独立维护 Git 仓库，要求：

- 保持有意义的提交记录，不要最后一天一次性提交全部代码。
- 提供 `.gitignore`，不提交 `bin/`、`obj/`、`node_modules/`、Python 虚拟环境、IDE 缓存或敏感配置。
- 提供 `README.md`，至少包括项目介绍、技术栈、目录结构、数据库初始化、启动步骤、配置说明、测试运行方式、已实现功能和未完成项。
- 提供 ER 图、建表脚本 / Migration、Swagger / OpenAPI 文档。
- 保证在新环境按 README 可以启动前端、后端和数据库。
- 提供测试代码及运行结果，并在 README 中提供第十节项目文档入口。

**最终交付：** Git 仓库地址（或压缩包）+ 前端代码 + 后端代码 + README + 数据库初始化文件 + 测试代码 + 项目文档。无需制作 PPT。

## 九、可选拓展功能

完成全部必做需求后，可按剩余时间自行选择，不作为必做要求：

- **驳回后修改并重新提交**：申请人修改被驳回的申请后重新发起完整两级审批；需保留原审批历史并区分审批轮次。
- **撤回申请**：仅在审批未结束时允许申请人撤回，并明确状态及历史记录规则。
- **Docker Compose**：一条命令启动前后端和数据库。
- **额外集成测试**：覆盖 HTTP API、身份认证、数据库事务及并发行为。

拓展功能以实际效果和技术理解为主，不要求全部完成；如实现拓展，需在 Spec 中明确新增规则，不能破坏基础流程。

| 技术设计与决策 | ER 图、OpenAPI 入口、关键代码位置，以及审批权限、状态流转、事务、并发防重复的设计理由；实质变更应记录原因、影响和验证结果。 |

文档可以独立建档，也可放在 README 或 Spec 的相应章节。每条需求、业务规则和技术约定应有一个主要维护位置，其他位置通过链接引用。

### 编写与更新

1. **第 1 天**完成需求边界和开发规范初稿。核心规则明确谁能操作、适用条件、成功结果和失败行为。
2. **开发期间**随代码同步更新相关文档。普通需求可在同一份 Spec 记录范围、方案、任务和验证；独立评审或验收材料可拆成附件。
3. **第 5 天**核对文档、代码和实际行为，分别记录实现、部署和验收状态；验证证据注明环境、命令或操作步骤及结果，未执行项如实标明。

### 验收

- 从 README 能找到需求边界、开发规范和技术设计。
- 抽查一条核心规则（如“一级审批通过后进入二级审批”或“审批历史写入失败时事务回滚”），能从需求定位到实现及测试或手动验证步骤。
- 在新环境按 README 验证初始化、启动和测试步骤。
